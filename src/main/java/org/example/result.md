
## S-Single Responsibility Principle

В исходном коде метод processOrder совмещал сразу пять обязанностей:
валидировал заказ, считал скидку, считал комиссию, печатал чек и сохранял заказ.
Теперь каждая из обязанностей вынесена в соответствующий ей класс.
OrderService только оркестрирует шаги, вызывая их в нужном порядке.

## O-Open/Closed Principle

Раньше, чтобы добавить новый тип клиента или оплаты,
надо было влезть в if/else внутри processOrder.
Теперь для нового тарифа достаточно написать свой класс-стратегию и зарегистрировать его одной строкой.
OrderService и уже существующие стратегии при этом вообще не трогаются.

## L-Liskov Substitution Principle

В исходном коде расчёты скидок и комиссии были зашиты в условные конструкции в самом сервисе.
Из-за этого нельзя было подставить другую реализацию расчёта, не меняя метод processOrder.
Теперь у расчётов скидки и комиссии свои контракты и реализации.
Любую реализацию можно подставить в OrderService без изменения его поведения.

## I-Interface Segregation Principle

В исходном коде был один класс OrderService, который умел всё сразу.
Если бы кому-то понадобился только расчёт комиссии, ему пришлось бы тянуть класс со всем функционалом.
Были добавлены интерфейсы по одному методу
каждый из них отвечает за одну задачу, и не зависит от остальных.

## D-Dependency Inversion Principle

Раньше сервис внутри себя сам проводил полный цикл работы с заказом,
по правилам указанным в самом же сервисе.
Сменить, к примеру, способ отправки чека было невозможно без правки сервиса.
То есть модуль высокого уровня зависел от конкретных деталей реализации, а не от абстракций.
После рефакторинга сервис принимает через конструктор только абстракции,
а какие конкретно реализации будут использованы решаются вне OrderService.
